# 쿠피(Coupi) — 상세 설계 문서 세트

## 📛 앱 이름 (2026-09-21 확정)

앱 이름을 **쿠피(Coupi)**로 확정했다. 문서 내에서 "메일 쿠폰 알림 앱"으로 지칭하던 부분은 실제 코드/스토어 등록 시 "쿠피" 또는 "Coupi"로 대체한다 (패키지명, 앱 아이콘, 스토어 등록명 등).

## 🤖 MVP는 LLM(AI 모델)을 사용하지 않는다 (2026-09-21 확정)

쿠폰 판별 파이프라인의 2단계(원래 LLM이 담당하던 "실사용 가능 여부 판정")를 **규칙/정규식 기반 추출·판정 로직**으로 대체한다. 이유는 비용 부담(호출량에 비례해 계속 발생하는 API 요금)과 복잡도를 낮춰 빠르게 MVP를 배포하기 위함이다. 대신 다음을 감수한다.

- LLM 대비 판별 정밀도가 낮을 수 있음 (특히 발신자 전용 파서가 없는 메일)
- 만료일을 정규식으로 못 찾으면 보수적으로 발송을 보류함 (미탐지 발생 가능)
- 발신자별 전용 파서를 베타 기간 동안 계속 추가해나가는 운영 부담이 생김

LLM 도입은 MVP 출시 이후, 실제 오탐지/미탐지 비율을 측정해본 뒤 필요성이 확인되면 재검토하는 것으로 미뤘다. 아키텍처는 `CouponExtractor` 인터페이스로 추상화해 나중에 LLM을 추가해도 구조를 갈아엎지 않도록 설계했다 (`02-쿠폰판별로직.md` 참고).

## ⚠️ 범위 변경 안내 (2026-09-21)

**메일 제공자를 Gmail 단독으로 한정한다. 네이버 메일 연동은 지원하지 않는다.**

네이버 메일은 공식 OAuth API가 없어 IMAP + 사용자가 직접 발급하는 "앱 비밀번호"를 서버에 저장하는 방식으로만 연동이 가능했다. 이는 (1) 계정 로그인 비밀번호 자체는 아니지만 서버가 상시 보관하는 로그인 자격증명이라는 점에서 OAuth 토큰보다 유출 위험이 크고, (2) 네이버가 제3자 앱의 이런 저장 방식을 공식적으로 승인/보증하지 않아 법적 근거가 불명확하다는 두 가지 이유로 리스크가 크다고 판단해 제외했다. 원본 설계 문서와 이 문서 세트의 초안에는 네이버 관련 설계가 남아있었으나, 이번 개정에서 전부 제거하거나 "지원하지 않음"으로 표기했다.

## 이 문서 세트의 목적

기존 아키텍처 설계 문서(이하 "원본 설계")는 전체 시스템의 구조와 방향을 정의했지만, 실제 개발에 들어가기 전에 확정되어야 할 세부 사항 — API 스펙, DB 스키마, LLM 프롬프트 형식, 실패 시나리오 대응 등 — 은 아직 구체화되지 않았다. 이 문서 세트는 원본 설계를 주제별로 쪼개어, 개발 착수 전 "설계 공백"을 메우는 것을 목표로 한다.

원본 설계 파일(`메일_쿠폰_알림_앱_기술_아키텍처_설계.md`) 자체는 최초 작성 시점의 기록으로 두고 별도로 수정하지 않았다 — 원본에는 여전히 네이버 메일 연동 내용이 남아있으니, 실제 구현 기준은 반드시 이 문서 세트(범위 변경이 반영된 `docs/` 폴더)를 따른다. 이 문서들은 원본을 대체하는 것이 아니라, 각 섹션을 구현 가능한 수준까지 파고든 보완 자료이되, 이번 개정으로 범위가 Gmail 단독으로 좁혀졌다는 점이 원본과의 가장 큰 차이다.

## 남은 확인 사항 (결정이 아니라 사실 확인)

- **CASA 심사 대상 여부와 비용** — `gmail.readonly`는 Google의 restricted scope에 해당해 정식 출시 시 CASA 보안 평가 대상이 될 가능성이 높고, Tier 2 평가는 외부 심사 기관 비용이 발생한다. 금액과 대상 여부에 따라 로드맵 4단계 기간은 물론 프로젝트 규모 자체를 조정해야 할 수 있으므로, 다른 착수 작업보다 먼저 확인한다 (`07-보안개인정보.md`, `09-배포및로드맵.md`).
