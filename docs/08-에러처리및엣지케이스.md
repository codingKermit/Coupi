# 08. 에러 처리 및 엣지케이스 설계 ★ 신규 심화

> **범위 변경 (2026-09-21)**: Gmail 단독 지원으로 한정됨에 따라 네이버 IMAP 관련 실패 시나리오를 제거했다 (`00-개요.md` 참고).

원본 설계에는 없던 영역으로, 각 컴포넌트의 실패 지점과 복구 전략을 이번 라운드에서 새로 정리했다. "정상 흐름"만 설계된 상태로 개발을 시작하면 운영 단계에서 반복적으로 장애가 발생하는 부분이므로 착수 전 확정을 권장한다.

## 1. 인증/토큰 관련

| 시나리오 | 감지 방법 | 대응 |
| --- | --- | --- |
| Gmail refresh token 만료/폐기(사용자가 Google 계정 설정에서 직접 앱 접근 취소) | API 호출 시 `invalid_grant` 에러 | `mail_accounts.status='reauth_required'`로 전환, watch/보정 폴링 중단, 사용자에게 재인증 요청 푸시 발송 (1회, 이후 앱 배너로만 유도) |
| Gmail Pub/Sub watch 갱신 실패 | `gmail-watch-renewal` 잡에서 API 오류 | 3회 재시도 후 실패 시 해당 계정은 `gmail-safety-poll`(6시간 주기 보정 폴링)에만 의존하는 상태로 전환 — Push가 끊겨도 서비스는 지속되도록 이중 안전장치. 단, 이 상태가 24시간 이상 지속되면 운영자에게 경보 |

## 2. 메일 수집 관련

| 시나리오 | 감지 방법 | 대응 |
| --- | --- | --- |
| Gmail webhook이 중복 전달됨 (Pub/Sub at-least-once 특성) | 동일 `historyId` 처리 시도 | `processed_mails` 유니크 제약(03번 문서)으로 DB 레벨에서 중복 삽입 차단, 애플리케이션은 unique violation을 정상 케이스로 처리(무시) |
| Gmail webhook 자체가 유실됨 (드물지만 발생 가능) | - | 안전망으로 6시간마다 모든 활성 Gmail 계정에 대해 `history.list` 재확인하는 보정 폴링 잡(`gmail-safety-poll`)을 낮은 우선순위로 병행 실행 |
| `historyId`가 만료되어 `404` 응답 | Gmail API 에러 코드 | 최근 24시간 메일을 `messages.list`로 전체 재조회 후 커서 재설정 (01번 문서 언급 내용을 여기서 절차화) |
| 매우 큰 첨부파일이 포함된 메일 | 본문 파싱 단계에서 크기 초과 | 첨부파일은 다운로드하지 않고 본문 텍스트만 추출 (Gmail API의 부분 조회 지원 활용), 본문 텍스트 자체가 비정상적으로 클 경우 4000자로 truncate 후 처리 (02번 문서와 연결) |

## 3. 쿠폰 판별(LLM) 관련

| 시나리오 | 감지 방법 | 대응 |
| --- | --- | --- |
| LLM API 타임아웃/5xx | HTTP 오류 | 최대 2회 재시도(지수 백오프), 이후 `processed_mails.filter_result='llm_failed'`로 기록하고 `pending_review` 큐에 5분 후 재처리 잡 등록 (최대 3회 재처리 시도 후 최종 폐기, 운영자 알림) |
| LLM이 스키마와 다른 형식으로 응답 (JSON 파싱 실패) | 파싱 에러 | 1회 즉시 재시도(동일 프롬프트), 재실패 시 위 `llm_failed` 흐름과 동일하게 처리 |
| LLM이 명백히 이상한 값 반환 (예: `expiry_date`가 과거보다 훨씬 이전이거나 10년 후) | 응답 후 validation 단계 | 서버 측에서 구조화 출력에 대한 sanity check 수행 (예: expiry_date가 오늘로부터 -1일~+365일 범위를 벗어나면 신뢰하지 않고 null 처리 + confidence를 강제로 0.5 이하로 하향) |
| 동일 사용자에게 짧은 시간 내 지나치게 많은 쿠폰이 판별됨 (스팸 메일함 대량 유입, 프로모션 메일 폭탄) | 시간당 발송 건수 카운트 | 사용자당 시간당 알림 발송 상한(예: 5건)을 두고 초과분은 다이제스트로 묶어 "오늘 도착한 쿠폰 7개 더 보기" 형태로 대체 발송 (알림 피로도 방지 — 원본 설계의 "정밀도" 목표와 직결) |

## 4. 푸시 발송 관련

04번 문서의 재시도 정책과 중복되지 않는 엣지케이스만 기술:

| 시나리오 | 대응 |
| --- | --- |
| 사용자가 여러 디바이스를 보유, 그중 일부 토큰만 무효 | 무효 토큰만 개별 삭제, 나머지 유효 디바이스에는 정상 발송 (부분 실패를 전체 실패로 취급하지 않음) |
| FCM 자체 장애(서비스 전면 장애) | 재시도 큐에 계속 쌓이도록 두고, 알림 통해 운영자에게 큐 적체 경보. 장애 해소 후 자동으로 소진됨 (수동 개입 최소화) |

## 5. 데이터 정합성 관련

| 시나리오 | 대응 |
| --- | --- |
| 사용자가 계정을 연결 해제한 직후에도 이미 큐에 들어간 잡이 처리되려는 경우 | 각 워커가 처리 시작 전 `mail_accounts.status='active'` 여부를 재확인(re-check)하고, active가 아니면 즉시 잡을 skip |
| 동일 사용자가 Gmail 계정을 두 번 연결 시도 (이미 연결된 계정) | `mail_accounts` 유니크 제약(`user_id, provider, provider_account_email`)으로 차단, API가 409 Conflict 반환 |
| 서버 배포 중 워커가 재시작되어 처리 중이던 잡이 유실 | BullMQ의 job persistence(Redis 기반) 특성상 ack 되지 않은 잡은 자동으로 재할당됨 — 단, 워커 로직은 반드시 멱등(idempotent)하게 작성 (동일 잡이 두 번 실행되어도 부작용 없도록, 예: INSERT 대신 `ON CONFLICT DO NOTHING`) |

## 운영 알림(Alerting) 기준 요약

다음 조건이 발생하면 Datadog/Sentry를 통해 운영 슬랙 채널에 즉시 경보:

- 특정 큐의 대기(waiting) 작업이 임계치(예: 1,000건) 초과
- LLM 호출 실패율이 5분간 20% 초과
- `auth_failed`/`reauth_required` 상태로 전환되는 계정 수가 시간당 급증 (제공자 측 정책 변경 조기 감지)
- 푸시 발송 실패율이 10% 초과
