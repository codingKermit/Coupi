# 08. 에러 처리 및 엣지케이스 설계 ★ 신규 심화

> **범위 변경 (2026-09-21)**: Gmail 단독 지원으로 한정됨에 따라 네이버 IMAP 관련 실패 시나리오를 제거했다 (`00-개요.md` 참고).
>
> **스택 확정 반영 (2026-09-22)**: 큐가 Redis + BullMQ에서 Pub/Sub + Cloud Tasks로 바뀌면서 재시도·잡 유실·알림 기준을 해당 서비스 기준으로 다시 작성했다 (`05-백엔드아키텍처.md`, `10-기술스택결정.md`).

원본 설계에는 없던 영역으로, 각 컴포넌트의 실패 지점과 복구 전략을 이번 라운드에서 새로 정리했다. "정상 흐름"만 설계된 상태로 개발을 시작하면 운영 단계에서 반복적으로 장애가 발생하는 부분이므로 착수 전 확정을 권장한다.

## 1. 인증/토큰 관련

| 시나리오 | 감지 방법 | 대응 |
| --- | --- | --- |
| Gmail refresh token 만료/폐기(사용자가 Google 계정 설정에서 직접 앱 접근 취소) | API 호출 시 `invalid_grant` 에러 | `mail_accounts.status='reauth_required'`로 전환, watch/보정 폴링 중단, 사용자에게 재인증 요청 푸시 발송 (1회, 이후 앱 배너로만 유도) |
| Gmail Pub/Sub watch 갱신 실패 | `gmail-watch-renewal` Job에서 API 오류 | 3회 재시도 후 실패 시 해당 계정은 `gmail-safety-poll`(6시간 주기 보정 폴링)에만 의존하는 상태로 전환 — Push가 끊겨도 서비스는 지속되도록 이중 안전장치. 단, 이 상태가 24시간 이상 지속되면 운영자에게 경보 |

## 2. 메일 수집 관련

| 시나리오 | 감지 방법 | 대응 |
| --- | --- | --- |
| Gmail webhook이 중복 전달됨 (Pub/Sub at-least-once 특성) | 동일 `historyId` 처리 시도 | `processed_mails` 유니크 제약(03번 문서)으로 DB 레벨에서 중복 삽입 차단, 애플리케이션은 unique violation을 정상 케이스로 처리(무시) |
| Gmail webhook 자체가 유실됨 (드물지만 발생 가능) | - | 안전망으로 6시간마다 모든 활성 Gmail 계정에 대해 `history.list` 재확인하는 보정 폴링 Job(`gmail-safety-poll`)을 병행 실행 |
| `historyId`가 만료되어 `404` 응답 | Gmail API 에러 코드 | 최근 24시간 메일을 `messages.list`로 전체 재조회 후 커서 재설정 (01번 문서 언급 내용을 여기서 절차화) |
| 매우 큰 첨부파일이 포함된 메일 | 본문 파싱 단계에서 크기 초과 | 첨부파일은 다운로드하지 않고 본문 텍스트만 추출 (Gmail API의 부분 조회 지원 활용), 본문 텍스트 자체가 비정상적으로 클 경우 4000자로 truncate 후 처리 (02번 문서와 연결) |
| 핸들러가 Pub/Sub ack 기한(ack deadline) 안에 끝나지 않음 | 같은 메시지가 반복 재전달됨 | 처리 시간이 긴 작업은 즉시 ack 후 Cloud Tasks로 넘겨 분리하거나, 구독의 ack deadline을 늘린다. 재전달 자체는 멱등 처리로 무해해야 한다 |

## 3. 쿠폰 판별(규칙 기반, MVP: LLM 미사용) 관련

> 범위 변경(2026-09-21)으로 MVP는 LLM을 사용하지 않으므로, 아래 시나리오는 정규식 추출/판정 파이프라인(`02-쿠폰판별로직.md`) 기준으로 다시 작성했다.

| 시나리오 | 감지 방법 | 대응 |
| --- | --- | --- |
| 발신자 전용 파서도, 범용 정규식도 만료일을 못 찾음 | `extract()`가 `expiryDate: null` 반환 | `processed_mails.filter_result='extraction_failed'`로 기록, 발송하지 않고 보수적으로 보류. 주간 리뷰에서 빈도 높은 발신자를 전용 파서 추가 대상으로 선정 |
| 정규식이 날짜를 잘못 파싱함 (예: 본문 속 다른 숫자를 날짜로 오인) | 파싱된 `expiryDate`가 **메일 수신일 기준** 타당 범위(수신일 −1일 ~ 수신일 +365일)를 벗어남 | sanity check 통과 못하면 `expiryDate`를 신뢰하지 않고 null 처리 → 위 "만료일 못 찾음" 흐름과 동일하게 보류 처리. **기준을 "오늘"이 아니라 "수신일"로 잡는 이유**: 정상적으로 만료된 쿠폰까지 `extraction_failed`로 분류되면 보류 통계가 오염되어 파서 보강 우선순위를 못 정한다 (범위 표는 `02-쿠폰판별로직.md` "만료일 타당성 검사 기준") |
| 발신자 전용 파서가 메일 포맷 변경으로 더 이상 매칭되지 않음 (쇼핑몰이 템플릿을 바꾼 경우) | 특정 `extractor_id`의 `extraction_failed` 비율이 갑자기 급증 | 대시보드 알림(05번 문서)으로 감지, 해당 파서를 새 포맷에 맞게 긴급 수정. 임시로는 범용 정규식 파서로 자동 폴백되므로 완전 서비스 중단은 아님 |
| 동일 사용자에게 짧은 시간 내 지나치게 많은 쿠폰이 판별됨 (스팸 메일함 대량 유입, 프로모션 메일 폭탄) | 시간당 발송 건수 카운트 | 사용자당 시간당 알림 발송 상한(예: 5건)을 두고 초과분은 다이제스트로 묶어 "오늘 도착한 쿠폰 7개 더 보기" 형태로 대체 발송 (알림 피로도 방지 — 원본 설계의 "정밀도" 목표와 직결) |

## 4. 푸시 발송 관련

04번 문서의 재시도 정책과 중복되지 않는 엣지케이스만 기술:

| 시나리오 | 대응 |
| --- | --- |
| 사용자가 여러 디바이스를 보유, 그중 일부 토큰만 무효 | 무효 토큰만 개별 삭제, 나머지 유효 디바이스에는 정상 발송 (부분 실패를 전체 실패로 취급하지 않음) |
| FCM 자체 장애(서비스 전면 장애) | `push-dispatch` Cloud Tasks 큐가 지수 백오프로 자동 재시도한다. 큐 깊이가 임계치를 넘으면 운영자에게 경보하고, 장애 해소 후 자동으로 소진되게 둔다 (수동 개입 최소화). 장기 장애 시에는 큐를 일시 정지(`pause`)해 `max_attempts` 소진을 막는다 |

## 5. 데이터 정합성 관련

| 시나리오 | 대응 |
| --- | --- |
| 사용자가 계정을 연결 해제한 직후에도 이미 큐에 들어간 작업이 처리되려는 경우 | 각 핸들러가 처리 시작 전 `mail_accounts.status='active'` 여부를 재확인(re-check)하고, active가 아니면 즉시 skip하고 ack |
| 동일 사용자가 Gmail 계정을 두 번 연결 시도 (이미 연결된 계정) | `mail_accounts` 유니크 제약(`user_id, provider, provider_account_email`)으로 차단, API가 409 Conflict 반환 |
| 배포 중 인스턴스가 교체되어 처리 중이던 작업이 중단됨 | Pub/Sub와 Cloud Tasks 모두 **ack(2xx 응답)를 받아야 완료로 간주**하므로, 중단된 작업은 자동으로 재전달된다. 단 이는 at-least-once이므로 **핸들러는 반드시 멱등하게 작성**한다 (INSERT 대신 `ON CONFLICT DO NOTHING`, 발송 전 이력 확인 등) |
| 재시도를 모두 소진한 메시지 | Pub/Sub는 dead letter topic으로 자동 이동한다. 이 토픽에 메시지가 쌓이면 즉시 경보하고 원인 확인 후 수동 재처리한다. Cloud Tasks는 소진 시 실패 로그만 남으므로 로그 기반 알림 정책을 건다 |

## 운영 알림(Alerting) 기준 요약

다음 조건이 발생하면 **Cloud Monitoring 알림 정책**(+ 애플리케이션 예외는 Sentry)으로 경보한다. 통지 채널은 이메일로 시작하고, 필요 시 Slack 웹훅을 추가한다.

- Pub/Sub 구독의 `oldest_unacked_message_age`가 임계치(예: 10분) 초과 — 처리 적체
- **dead letter topic에 메시지가 1건이라도 유입** — 재시도 소진 실패, 즉시 확인
- Cloud Tasks 큐 깊이가 임계치 초과, 또는 작업 실패율 급증
- Cloud Run 5xx 비율 5% 초과, 또는 인스턴스가 `max-instances`에 지속적으로 도달
- 특정 `extractor_id`의 `extraction_failed` 비율이 5분간 30% 초과 (메일 포맷 변경 조기 감지)
- `auth_failed`/`reauth_required` 상태로 전환되는 계정 수가 시간당 급증 (제공자 측 정책 변경 조기 감지)
- 푸시 발송 실패율이 10% 초과
