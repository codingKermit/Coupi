## 항목별 근거

### 클라우드 — GCP 단독

Gmail watch 알림은 반드시 GCP Pub/Sub 토픽으로 수신되고, OAuth 동의화면·심사와 FCM도 모두 GCP/Firebase다. GCP는 어차피 회피할 수 없다. 여기에 AWS를 더하면 1인 운영에서 계정·IAM·네트워크 경계가 두 벌이 된다.

### 실행 환경 — Cloud Run

베타 트래픽은 사실상 0에 가깝다. Cloud Run은 scale-to-zero로 유휴 비용이 없고, Gmail webhook 수신에 필요한 HTTPS 엔드포인트가 자동으로 붙는다. GKE는 클러스터 고정비와 운영 부담이 이 규모에 맞지 않는다.

Pub/Sub push 구독과 Cloud Tasks는 모두 **HTTP POST로 작업을 전달**하므로, 워커도 상주 프로세스가 아니라 요청 기반 서비스가 된다. 따라서 API와 워커 모두 `min-instances=0`으로 두어 유휴 비용이 없다. 대가는 유휴 후 첫 요청의 콜드 스타트인데, 성공 기준이 "수 분 이내 알림"이므로 허용 범위다. 배치(watch 갱신, 6시간 보정 폴링)는 Cloud Scheduler가 Cloud Run Jobs를 호출하는 형태로 구성한다.

### 큐 — Redis + BullMQ 대신 Pub/Sub + Cloud Tasks

원본 설계의 Redis + BullMQ는 서버리스 실행 환경과 궁합이 나쁘다. GCP 관리형 Redis(Memorystore)는 최소 인스턴스에도 월 고정비가 붙고 VPC 커넥터가 필요해, Cloud Run의 scale-to-zero 이점을 상쇄한다.

반면 Gmail watch가 **이미 Pub/Sub를 사용**하므로 수집 큐로 재사용하면 추가 인프라가 없다. Cloud Tasks는 지연 예약과 재시도가 내장되어 있어 만료 임박 리마인더에 그대로 맞는다. 둘 다 이 규모에서는 무료 티어 범위다.

**대가**: BullMQ의 대시보드(Bull Board)와 로컬 개발 편의를 잃는다. 로컬에서는 Pub/Sub 에뮬레이터를 사용한다.

### 웹 프레임워크 — NestJS

개발을 전면 위임하므로 러닝커브는 선택 기준에서 빠진다. 대신 두 가지가 중요해진다.

1. `05-백엔드아키텍처.md`의 모듈/폴더 구조가 이미 NestJS 전제로 작성되어 있다 — 다른 선택은 문서 재작성을 유발한다.
2. NestJS는 데코레이터·DI·모듈 규약이 강해 세션이 나뉘어도 코드 스타일이 일관되게 유지된다. 규약이 약한 프레임워크는 작업 세션마다 구조가 흔들리기 쉽다.

`AuthService` / `MailIngestService` / `CouponClassifierService` / `NotificationService` / `UserService` 5개 모듈 분리에도 잘 맞는다.

**대가**: 사용자가 프레임워크를 모르는 상태이므로 유지보수가 에이전트에 의존하게 된다. 이는 전면 위임 결정에 이미 내포된 사항이다.

### 데이터베이스 — Cloud SQL

Neon·Supabase 같은 서버리스 PostgreSQL은 무료 티어와 scale-to-zero가 매력적이지만, **암호화된 Gmail refresh token이 제3자 인프라에 저장**된다. CASA 백서에 하위 처리자를 별도로 기술해야 하고 심사 설명이 복잡해진다. 얻는 비용 절감보다 심사 리스크가 크다.

`03-API-DB-스펙.md`의 스키마가 PostgreSQL 문법으로 작성되어 있으므로 DB 엔진 자체는 유지한다.


### dev 데이터베이스는 Neon (2026-09-30 추가 결정)

운영은 위 결정대로 Cloud SQL을 쓰되, **개발 환경은 Neon(무료 서버리스 Postgres)** 을 쓴다.
로컬에 DB 서버를 두지 않기로 했고, GCP 계정이 아직 없어 Cloud SQL을 띄울 수 없기 때문이다.

| 검토 | 결과 |
| --- | --- |
| Neon | **채택.** 진짜 PostgreSQL, 프로젝트당 0.5GB·월 100 compute-hours, 5분 무활동 시 scale-to-zero, **무활동 정지 없음**, 브랜칭 지원 |
| Supabase | 같은 무료 용량이지만 **1주 무활동 시 프로젝트 자동 정지** → 간헐적 개발 리듬과 맞지 않는다. 안 쓰는 auth/storage/realtime이 딸려온다 |
| CockroachDB 등 PG 호환 | 배제. 스키마가 `gen_random_uuid()`, CHECK 제약, 부분 인덱스, JSONB를 쓰므로 호환 구현으로는 위험하다 |

용량은 넉넉하다. 메일 원문을 저장하지 않는 설계라(`03-API-DB-스펙.md`) 실제로 쌓이는 것은
제목·발신자·쿠폰 메타데이터뿐이다.

**브랜칭이 이 프로젝트에 특히 유용하다.** `backend/prisma/README.md`의 CHECK 제약 수동 반영
절차는 아직 실제로 검증되지 않았는데, 브랜치에서 시험하고 틀리면 버릴 수 있다.

**운영에 Neon을 쓰지 않는 이유는 그대로다.** 암호화된 Gmail refresh token이 제3자 인프라에
저장되면 CASA 보안 백서에 하위 처리자를 따로 기술해야 한다 (위 "데이터베이스" 절).

**주의**: 발신자 집계(`02-쿠폰판별로직.md`)를 위해 본인·지인의 실제 Gmail 계정을 dev에 연결하면
그 시점부터 실제 refresh token이 Neon에 저장된다. 심사 대상은 아니지만, 집계가 끝나면
`DELETE /mail-accounts/:id`로 연결을 해제해 토큰을 지운다.

**연결 설정**: Neon은 풀링(pgbouncer)과 직접 연결 엔드포인트가 나뉘어 있다. `prisma migrate`는
세션 수준 기능(advisory lock 등)을 쓰므로 직접 연결이 필요해, `schema.prisma`에 `directUrl`을
두고 환경변수를 `DATABASE_URL`(풀링)과 `DIRECT_DATABASE_URL`(직접)로 나눴다.
### 모바일 — Expo (선택이 아닌 요구사항)

macOS가 없으면 로컬에서 iOS 빌드를 만들 수 없다. **EAS Build(클라우드 빌드)가 유일한 경로**이므로 Expo를 사용한다. 현재 요구 기능 — FCM 푸시, 딥링크, OAuth 웹뷰, 백그라운드 수신 — 은 모두 Expo development build 범위 안에 있어 bare workflow로 나갈 이유가 없다.

**대가**: EAS 무료 티어에는 월 빌드 횟수 제한이 있다. 빌드가 잦아지면 유료 전환이 필요하다.

### 인프라 관리 — Terraform

사용자가 GCP 콘솔을 직접 조작하지 않기로 했으므로, 인프라는 코드로 정의하고 사용자는 `terraform apply` 실행과 결과 확인만 한다. 콘솔 클릭으로 만든 리소스는 재현이 불가능해 dev/prod 이중 구성과 재해 복구에 불리하다.

### 환경 — dev + prod 2개

베타 100명 규모에서 3환경은 고정비가 3배가 된다. staging은 3단계(내부 베타) 진입 시 추가한다. 단 **Gmail OAuth 클라이언트 ID는 환경별로 분리**한다 (`05-백엔드아키텍처.md`) — 미검증 상태 테스트가 production에 영향을 주지 않도록.

## 비용 관점

고정비가 발생하는 항목은 **Cloud SQL 인스턴스 하나뿐이다.** Cloud Run은 요청이 없으면 0으로 내려가고, Pub/Sub, Cloud Tasks, Cloud Scheduler, FCM, Sentry 무료 티어, Cloud Logging은 이 트래픽 규모에서 무료 범위에 머문다.

> 구체적 금액은 리전·사양에 따라 편차가 크므로 **GCP 요금 계산기로 직접 확인한다**. 이 문서는 금액을 명시하지 않는다.
