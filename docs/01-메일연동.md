# 01. 메일 연동 상세 설계 (Gmail 단독)

> **범위 변경 (2026-09-21)**: 네이버 메일 연동은 지원하지 않는다. 사유는 `00-개요.md`의 "범위 변경 안내"와 `07-보안개인정보.md`를 참고. 이 문서는 원본 설계의 "메일 접근 방식 설계", "신규 메일 실시간 감지" 섹션 중 Gmail 관련 부분만 구현 가능한 수준으로 구체화한다.

## MailProvider 인터페이스

현재는 Gmail 하나만 구현하지만, 향후 다른 제공자(예: 네이버가 공식 API를 제공하게 되거나, 기업용 메일 등)를 다시 검토할 가능성에 대비해 인터페이스 자체는 특정 제공자에 종속되지 않도록 유지한다. 다만 지금 단계에서 실제로 구현/테스트하는 구현체는 `GmailProvider` 하나뿐이다.

```ts
interface MailProvider {
  readonly providerName: 'gmail';   // 현재는 'gmail' 단일 값만 존재

  // OAuth/인증 관련
  getAuthUrl(state: string): string;
  exchangeCodeForToken(code: string): Promise<ProviderTokenSet>;
  refreshAccessToken(refreshToken: string): Promise<ProviderTokenSet>;
  revokeToken(refreshToken: string): Promise<void>;

  // 메일 수집 관련
  registerWatch(userId: string, token: ProviderTokenSet): Promise<WatchHandle>;
  // Gmail: Pub/Sub watch 등록

  fetchNewMessages(userId: string, cursor: ProviderCursor): Promise<{
    messages: RawMailMessage[];
    nextCursor: ProviderCursor;
  }>;
  // Gmail: historyId 기반

  fetchMessageBody(userId: string, messageId: string): Promise<MailBody>;
}

interface ProviderTokenSet {
  accessToken: string;
  refreshToken: string;
  expiresAt: Date;
  scope: string[];
}

interface RawMailMessage {
  providerMessageId: string;   // Gmail message id
  from: string;
  subject: string;
  receivedAt: Date;
}

interface MailBody {
  html?: string;
  text?: string;
}
```

`ProviderCursor`는 Gmail의 `historyId: string`을 감싼다. DB에 저장되는 `mail_accounts.cursor` 컬럼(JSONB)에 그대로 직렬화한다.

## Gmail 구현 세부사항

### OAuth 스코프
- 1차 목표: `https://www.googleapis.com/auth/gmail.readonly`
- 검토 대상: `gmail.metadata` — 본문 없이 제목/발신자만 필요한 규칙 필터 단계에서는 이 스코프로 충분할 수 있음. 다만 2단계 구조화 추출(정규식 파서, `02-쿠폰판별로직.md`)에는 본문이 필요하므로, **본문이 필요한 사용자에게만 readonly를 요청하는 점진적 동의(incremental consent)** 방식은 Google API 정책상 지원되지 않으므로 처음부터 `gmail.readonly`로 통일한다.
- `gmail.modify`, `gmail.send` 등 쓰기/발송 권한은 어떤 경우에도 요청하지 않는다.

### Pub/Sub Watch 갱신 배치
- `users.watch()`는 7일 후 만료되므로, 매일 00:00 UTC에 만료 3일 이내로 남은 계정을 재구독하는 크론 작업이 필요하다.
- 실패 시(토큰 만료, revoke됨 등) 해당 계정을 `mail_accounts.status = 'reauth_required'`로 표시하고, 사용자에게 재로그인을 요청하는 푸시를 보낸다.
- 실행 방식: `gmail-watch-renewal` Cloud Run Job을 Cloud Scheduler가 매일 00:00 UTC에 호출한다 (`05-백엔드아키텍처.md`).

### Webhook 수신기
- 엔드포인트: `POST /webhooks/gmail`
- Pub/Sub push 구독의 페이로드는 `{ message: { data: base64(JSON), messageId, publishTime }, subscription }` 형태. `data`를 디코딩하면 `{ emailAddress, historyId }`.
- **검증**: Pub/Sub push 요청은 Google이 서명한 JWT를 `Authorization: Bearer <token>` 헤더로 보낸다. 반드시 `google-auth-library`로 토큰 검증 후 처리 (스푸핑 방지).
- 수신 즉시 `{ userId, historyId }`를 `mail-ingest` 큐에 넣고 200 응답 (Pub/Sub는 응답 지연 시 재전송하므로 처리 로직은 큐 워커로 분리).

### 신규 메일 조회
- `history.list({ userId, startHistoryId, historyTypes: ['messageAdded'] })` 호출로 변경분 조회
- `startHistoryId`가 너무 오래되어 만료된 경우(`404` 응답) → 전체 재동기화 필요: 최근 N시간 이내 메일을 `messages.list`로 재조회 후 `historyId`를 최신화

### 안전망: 보정 폴링
- Pub/Sub webhook이 드물게 유실될 가능성에 대비해, 6시간마다 모든 활성 Gmail 계정에 대해 `history.list`로 재확인하는 낮은 우선순위의 보정 잡(`gmail-safety-poll`)을 병행 운영한다 (08번 문서 참고). Gmail 단독 연동이므로 상시 폴링 워커를 별도로 둘 필요는 없고, 이 보정 잡 하나로 충분하다.


> **구현 시 결정 (2026-09-22)**: 수집 단계의 규칙 필터는 **메타데이터(발신자·제목)만** 본다.
> 본문은 필터를 통과한 메일에 대해서만 판별 단계에서 받는다. 받은메일함의 모든 메일에 대해
> 본문을 내려받으면 Gmail API 할당량을 크게 쓰고, 접근 최소화 원칙(`07-보안개인정보.md`)에도
> 어긋나기 때문이다.
>
> **대가**: 제목에는 없고 본문에만 키워드가 있는 프로모션 메일은 놓친다. 화이트리스트에
> 등록된 발신자는 키워드를 보지 않고 통과하므로, 발신자 집계로 `filter_domains`를 채우는
> 작업(`02-쿠폰판별로직.md` "초기 지원 발신자 선정 절차")이 이 손실을 메우는 주된 수단이다.
> 베타에서 미탐지가 크면 통과 기준을 다시 검토한다.

## 중복 제거

- 동일 메일이 여러 경로(예: 재시도, webhook 중복 전달, 보정 폴링과 webhook 중복)로 두 번 들어올 수 있으므로, `processed_mails` 테이블에 `(mail_account_id, provider_message_id)` 유니크 제약을 걸어 중복 처리를 원천 차단한다 (자세한 스키마는 03번 문서 참고).

## 온보딩 UX

- 원본 설계에 있던 "메일 서비스 선택(Gmail/네이버)" 화면은 제거하고, 온보딩은 곧바로 "Gmail로 시작하기" 단일 진입점으로 단순화한다 (06번 문서 참고).
- 권한 안내 화면에서 "읽기 전용으로만 접근하며 메일 본문은 서버에 저장하지 않습니다"를 명확히 고지한 뒤 Google OAuth 동의 화면으로 이동한다.

## 지원 범위 안내 문구 (앱 내)

Gmail 외 메일 서비스 사용자에게는 온보딩/설정 화면에 **"현재 Gmail 계정만 지원합니다"라는 사실만 표기**한다 (2026-09-21 확정, `00-개요.md` 결정 #5). 향후 지원 예정 로드맵이나 사전 알림 신청 UI는 두지 않는다 — 네이버는 공식 API 경로가 없어 시점을 약속할 수 없기 때문이다.
