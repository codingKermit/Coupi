# 07. 보안 및 개인정보보호 심화 설계 ★ 심화

> **범위 변경 (2026-09-21)**: 메일 제공자를 Gmail 단독으로 한정했다. 원래 네이버 IMAP 연동을 위해서는 사용자가 발급한 "앱 비밀번호"(계정 로그인 비밀번호와는 다르지만, 서버가 상시 보관해야 하는 로그인 자격증명)를 저장해야 했는데, 이는 (1) OAuth 토큰보다 유출 시 피해 범위가 크고, (2) 네이버가 제3자 앱의 이런 저장 방식을 공식적으로 승인하지 않아 법적 근거가 불명확하다는 두 가지 이유로 리스크가 크다고 판단해 제외했다 (`00-개요.md` 참고). 이에 따라 이 문서에서도 네이버 관련 저장/폐기 정책을 모두 제거했다.

원본 설계의 "보안 및 개인정보보호 고려사항"을 실제 구현 정책 수준까지 심화한다.

## 암호화 키 관리

### Envelope Encryption 구조
- KMS(AWS KMS 또는 GCP KMS)에 마스터 키(CMK)를 두고, 이 마스터 키로 데이터 암호화 키(DEK)를 감싸는 envelope encryption 방식 사용
- `mail_accounts.encrypted_refresh_token`은 DEK로 AES-256-GCM 암호화 후 저장, DEK 자체는 KMS로 암호화되어 별도 컬럼 또는 설정에 보관
- 애플리케이션 서버는 매 요청마다 KMS를 호출해 평문 DEK를 얻는 대신, 짧은 TTL(예: 5분)로 메모리 캐시하여 KMS 호출량과 지연시간을 관리

### 키 로테이션 정책
- 마스터 키: 연 1회 로테이션 (KMS 자동 로테이션 기능 활용)
- DEK: 분기 1회 로테이션. 로테이션 시 기존 암호문을 즉시 재암호화하지 않고, "지연 재암호화(lazy re-encryption)" 방식 채택 — 토큰이 실제로 사용(refresh)될 때마다 새 DEK로 재암호화하여 저장. 배치로 강제 재암호화하는 별도 마이그레이션 잡도 준비해둔다 (키 완전 폐기 시한이 있는 경우 대비).

## 토큰 폐기(Revoke) 흐름

사용자가 계정 연결 해제를 요청했을 때(`DELETE /mail-accounts/:id`)의 정확한 순서:

```
1. mail_accounts.status를 즉시 'revoked'로 변경 (폴링/webhook 처리 중단)
2. 진행 중인 큐 잡이 있다면 해당 mailAccountId의 job을 취소 시도 (BullMQ job.remove())
3. Gmail revoke API 호출: `https://oauth2.googleapis.com/revoke?token={refresh_token}`
4. encrypted_refresh_token, encrypted_access_token 컬럼을 NULL로 덮어쓰기 (단순 논리 삭제가 아니라 실제 값 제거)
5. mail_accounts 레코드 자체는 감사 로그 목적으로 30일 보관 후 완전 삭제 (processed_mails, coupons는 CASCADE로 함께 삭제됨에 유의 — 사용자에게 "연결 해제 시 그동안 받은 쿠폰 기록도 삭제됩니다" 사전 고지 필요)
```

## 접근 범위 최소화 — 실무 체크리스트

- [ ] Gmail 요청 스코프가 `gmail.readonly` 하나로 고정되어 있고, `gmail.modify`/`gmail.send` 등 불필요 스코프가 코드 어디에도 요청되지 않는지 코드 리뷰 시 확인
- [ ] 로그에 메일 본문/제목 전문이 남지 않는지 정기 감사 (05번 문서의 로깅 원칙과 연결)

## Google CASA(Cloud Application Security Assessment) 대비 체크리스트

원본 설계는 "심사 대상이 될 수 있음"이라고만 언급했다. 실제 심사에서 요구되는 항목을 정리한다.

- [ ] 애플리케이션 보안 자가진단 설문(LOA: Letter of Assessment) Tier 확인 — 사용자 수/데이터 민감도에 따라 Tier 1~3 결정
- [ ] 취약점 스캔 리포트 준비 (OWASP 기반 자동 스캐너 결과, 또는 제3자 감사 기관 보고서)
- [ ] 데이터 암호화 증빙 (전송 중: TLS 1.2+, 저장 중: AES-256 — 위 암호화 섹션 내용을 백서화)
- [ ] 접근 통제 증빙 (RBAC, 운영자 계정의 사용자 데이터 접근 로그 기록 여부)
- [ ] 인시던트 대응 계획 문서 (데이터 유출 시 대응 절차, 통지 의무)
- [ ] 데이터 보관/삭제 정책 문서화 (위 "토큰 폐기 흐름" 및 "데이터 보관 정책"을 그대로 인용 가능)
- [ ] 서드파티 서브프로세서 목록 (LLM API 제공자, 클라우드 인프라 제공자 등 메일 데이터가 거쳐가는 모든 업체 명시)

## LLM 호출 시 개인정보 처리 원칙 (원본에 없던 추가 항목)

- 2단계 판별을 위해 메일 본문이 외부 LLM API로 전송되므로, 이는 "제3자 서브프로세서에게 개인정보를 위탁 처리"하는 행위에 해당한다. 개인정보처리방침에 이 사실을 명시해야 한다.
- LLM API 제공자가 요청 데이터를 자체 모델 학습에 사용하지 않는지(Zero Data Retention 옵션 등) 계약/약관 확인 필수 — Google Limited Use 정책과 마찬가지로 "명시된 기능에만 사용" 원칙을 LLM 벤더 선택 기준에도 동일하게 적용한다.
- 메일 본문을 LLM에 전송하기 직전, 발신자 이메일 주소 등 불필요한 개인식별정보는 마스킹하거나 제거하고 본문 텍스트만 전달하는 것을 원칙으로 한다.

## 데이터 보관 기간 요약표

| 데이터 | 보관 위치 | 보관 기간 |
| --- | --- | --- |
| 메일 본문 | 저장 안 함 (처리 직후 폐기) | - |
| 메일 제목/발신자 (`processed_mails`) | PostgreSQL | 90일 (분석/디버깅 목적, 이후 자동 삭제 배치) |
| 쿠폰 메타데이터 (`coupons`) | PostgreSQL | 만료 후 180일 (사용자가 지난 쿠폰 이력 조회 가능하도록), 이후 삭제 |
| OAuth Refresh Token | PostgreSQL (암호화) | 계정 연결 유지 중 계속, 연결 해제 시 즉시 삭제 |
| 디바이스 푸시 토큰 | PostgreSQL | 90일 미접속 시 삭제 |
| 애플리케이션 로그 | 로그 저장소 (본문/제목 미포함) | 30일 |
