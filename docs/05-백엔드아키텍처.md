# 05. 백엔드 아키텍처 상세 설계

> **범위 변경 (2026-09-21)**: Gmail 단독 지원으로 한정됨에 따라 네이버 폴링 워커/큐 관련 구성을 모두 제거했다. 또한 MVP는 LLM을 사용하지 않기로 결정해 `llm-classifier.service.ts`를 규칙 기반 추출기 모듈로 대체했다 (`00-개요.md`, `02-쿠폰판별로직.md` 참고).
>
> **스택 확정 반영 (2026-09-22)**: 기술 스택을 확정하면서 큐를 Redis + BullMQ에서 **Pub/Sub + Cloud Tasks**로, 실행 환경을 ECS/K8s에서 **Cloud Run**으로 교체했다. 환경도 3개에서 dev + prod 2개로 줄였다. 결정 근거는 `10-기술스택결정.md` 참고.

원본 설계의 기술 스택 표와 모듈 목록을 실제 폴더 구조/큐 설계 수준까지 구체화한다.

## 모듈/폴더 구조 (NestJS)

```
src/
  auth/                  # AuthService: OAuth 플로우, 세션 JWT 발급
    gmail.provider.ts
    mail-provider.interface.ts
  mail-ingest/           # MailIngestService: webhook 수신, 보정 폴링, 중복 제거
    gmail-webhook.controller.ts    # Pub/Sub push 수신 (Gmail watch 알림)
    mail-ingest.controller.ts      # Pub/Sub push 수신 (mail-ingest 토픽)
    mail-ingest.service.ts
    gmail-safety-poll.job.ts       # Cloud Run Job 진입점
  coupon-classifier/     # CouponClassifierService: 규칙 필터 + 정규식 추출/판정
    coupon-classify.controller.ts  # Pub/Sub push 수신 (coupon-classify 토픽)
    rule-filter.service.ts
    extractors/
      coupon-extractor.interface.ts
      generic-regex.extractor.ts
      coupang.extractor.ts         # 발신자 전용 파서 (베타 기간 계속 추가)
      baemin.extractor.ts
    validity-checker.service.ts    # 만료일 기반 usable_now 판정
  notification/          # NotificationService: FCM 발송, 재시도
    push-dispatch.controller.ts    # Cloud Tasks 타깃 엔드포인트
    fcm.client.ts
  user/                  # UserService: 계정/설정 관리
  coupons/               # Coupon CRUD 컨트롤러
  devices/               # Device 등록 컨트롤러
  jobs/                  # Cloud Run Jobs 진입점 모음 (watch 갱신, 보정 폴링)
  common/
    encryption/          # AES-256-GCM 유틸 (07번 문서 참고)
    messaging/           # Pub/Sub publisher, Cloud Tasks enqueuer 공통 모듈
    idempotency/         # 메시지 중복 수신 방어 (at-least-once 대응)
```

BullMQ의 `*.processor.ts`가 사라지고 **HTTP 컨트롤러**로 바뀐 것이 핵심 변화다. Pub/Sub push 구독과 Cloud Tasks는 모두 HTTP POST로 작업을 전달하므로, 워커는 상주 프로세스가 아니라 요청을 받는 서비스가 된다.

## 큐(Queue) 설계 상세

큐는 두 종류를 용도에 따라 나눠 쓴다.

- **Pub/Sub** — 이벤트 팬아웃형 처리(메일 감지 → 파싱 → 판별). Gmail watch 알림이 이미 Pub/Sub로 들어오므로 그대로 이어서 사용한다.
- **Cloud Tasks** — 개별 작업의 **지연 예약**과 **속도 제어**가 필요한 처리(푸시 발송, 만료 리마인더).

| 큐 | 종류 | 목적 | Producer | Consumer (엔드포인트) |
| --- | --- | --- | --- | --- |
| `gmail-notifications` | Pub/Sub 토픽 | Gmail watch 알림 수신 | Google (Gmail API) | `POST /internal/gmail/webhook` |
| `mail-ingest` | Pub/Sub 토픽 | 신규 메일 조회 → 파싱 트리거 | webhook 핸들러, 보정 폴링 Job | `POST /internal/mail-ingest` |
| `coupon-classify` | Pub/Sub 토픽 | 규칙 필터 + 정규식 추출/판정 (MVP: LLM 미사용) | mail-ingest 핸들러 | `POST /internal/coupon-classify` |
| `push-dispatch` | Cloud Tasks 큐 | FCM 발송 | classify 핸들러 | `POST /internal/push-dispatch` |
| `coupon-expiry-reminder` | Cloud Tasks 큐 | 만료 임박 리마인더 | 쿠폰 생성 시점에 **미리 예약** | `POST /internal/expiry-reminder` |

| 배치 | 실행 방식 | 주기 |
| --- | --- | --- |
| `gmail-watch-renewal` | Cloud Scheduler → Cloud Run Job | 매일 (watch 만료 7일 전 갱신) |
| `gmail-safety-poll` | Cloud Scheduler → Cloud Run Job | 매 6시간 |

### BullMQ 대비 달라지는 점

| 항목 | BullMQ에서 | 지금 |
| --- | --- | --- |
| 계정당 순서 보장 | 큐 concurrency를 계정당 1로 제한 | Pub/Sub **ordering key에 `mailAccountId`** 지정. 같은 계정 메시지는 순서대로 전달된다 |
| 동시성 제어 | 워커 concurrency 설정 | Cloud Run `max-instances` + 컨테이너당 동시 요청 수. Cloud Tasks는 큐 자체에 `max_dispatches_per_second` 설정 |
| 재시도 | BullMQ `attempts` + 백오프 | Pub/Sub 구독 재시도 정책(지수 백오프), Cloud Tasks `max_attempts` + 백오프 |
| DLQ | `*-failed` 큐 수동 구성 | Pub/Sub **dead letter topic** (최대 전달 횟수 초과 시 자동 이동). Cloud Tasks는 소진 시 실패 로깅 → Cloud Monitoring 알림 |
| 지연/예약 잡 | `delay` 옵션 | Cloud Tasks `schedule_time`. **만료 리마인더를 쿠폰 생성 시점에 바로 예약**할 수 있어, 매일 전체 스캔하던 배치가 불필요해졌다 |
| 대시보드 | Bull Board | Cloud Console의 Pub/Sub·Cloud Tasks 메트릭 + Cloud Monitoring 대시보드 |
| 로컬 개발 | Docker Redis | Pub/Sub 에뮬레이터 (`gcloud beta emulators pubsub`). Cloud Tasks는 에뮬레이터가 없어 **로컬에서는 타깃 엔드포인트를 직접 호출**하는 어댑터로 대체한다 |

### 멱등성 (필수)

Pub/Sub와 Cloud Tasks는 모두 **at-least-once** 전달이다. 같은 메시지가 두 번 올 수 있으므로 모든 핸들러는 멱등해야 한다.

- 메일 수집: `processed_mails`의 유니크 제약이 이미 이 역할을 한다 (`01-메일연동.md`, `03-API-DB-스펙.md`)
- 푸시 발송: 쿠폰 ID + 디바이스 토큰 조합으로 발송 이력을 확인한 뒤 발송
- 그 외: `common/idempotency/`에서 메시지 ID 기준으로 중복 수신을 걸러낸다

### 내부 엔드포인트 보호

`/internal/*` 경로는 외부에 노출되면 안 된다.

- Pub/Sub push 구독과 Cloud Tasks 모두 **OIDC 토큰**을 붙여 호출하도록 설정하고, 서비스 계정을 검증한다
- 워커 Cloud Run 서비스는 `ingress: internal-and-cloud-load-balancing`으로 제한한다
- 단, Gmail watch 알림을 받는 `gmail-notifications` 구독만은 Google이 발행하므로 별도로 **Pub/Sub JWT 검증**을 수행한다 (`01-메일연동.md`)

## 인프라 구성 (초기 규모 기준)

전부 Terraform으로 정의하고 콘솔 조작은 하지 않는다 (`10-기술스택결정.md`).

| 구성 요소 | 설정 |
| --- | --- |
| API 서비스 | Cloud Run, 공개 HTTPS(모바일 앱용 REST + Gmail webhook 수신), `min-instances=0` |
| 워커 서비스 | Cloud Run, 내부 전용, `min-instances=0`. Pub/Sub push와 Cloud Tasks가 HTTP로 깨우므로 상주할 필요가 없다 |
| 배치 | Cloud Run Jobs + Cloud Scheduler |
| 데이터베이스 | Cloud SQL (PostgreSQL), 단일 인스턴스 + 자동 백업. Cloud Run에서 Cloud SQL 커넥터로 접속. 사용자 증가 시 읽기 복제본 검토 |
| 비밀 관리 | Secret Manager에 OAuth 클라이언트 시크릿과 AES 마스터 키 저장, Cloud KMS로 감싸는 envelope encryption (`07-보안개인정보.md`) |
| 메시징 | Pub/Sub 토픽 3개 + dead letter topic, Cloud Tasks 큐 2개 |

**고정비가 발생하는 것은 Cloud SQL 인스턴스뿐이다.** Cloud Run은 요청이 없으면 0으로 내려가고, Pub/Sub·Cloud Tasks·Cloud Scheduler는 이 트래픽 규모에서 무료 티어 범위다.

**대가**: `min-instances=0`이면 유휴 후 첫 요청에 콜드 스타트가 붙는다. 성공 기준이 "신규 메일 도착 후 수 분 이내 알림"이므로 수 초의 콜드 스타트는 허용 범위다. 지연이 문제가 되면 워커만 `min-instances=1`로 올린다.

## 환경 분리

- `dev`(로컬 개발 + 테스트 계정)와 `prod` 2개 환경으로 시작한다. `staging`은 3단계(내부 베타) 진입 시 추가한다 (`10-기술스택결정.md`)
- **Gmail OAuth는 환경별로 별도 GCP 프로젝트/클라이언트 ID를 사용한다** — 심사 전 unverified 테스트가 production에 영향을 주지 않도록. 이 원칙은 환경을 2개로 줄여도 그대로 유지한다

## 로깅/모니터링 최소 셋업 (MVP 단계)

- **Cloud Logging / Cloud Monitoring**: Cloud Run을 쓰면 요청 로그·지연시간·인스턴스 수가 자동 수집된다. 별도 에이전트가 필요 없다
- **Sentry**(무료 티어): API + 워커 양쪽 연동, 릴리즈 태깅으로 배포 버전 추적
- 구조화 로그(JSON): `userId`(또는 해시), `mailAccountId`, `messageId`를 항상 포함해 특정 사용자의 처리 흐름을 추적 가능하게 함 — 단, 메일 제목/본문 등 콘텐츠는 로그에 남기지 않음 (`07-보안개인정보.md` 원칙과 연결)
- 핵심 대시보드 패널
  - Pub/Sub 구독별 `oldest_unacked_message_age` (처리 적체 감지)
  - Pub/Sub dead letter topic 메시지 수 (0이 아니면 즉시 확인)
  - Cloud Tasks 큐 깊이와 실패율
  - Cloud Run 요청 지연(p50/p95), 인스턴스 수, 5xx 비율
  - `extraction_failed` 비율 (발신자별)
  - 푸시 발송 성공률

알림 기준은 `08-에러처리및엣지케이스.md`의 Alerting 절을 따른다.
