# 05. 백엔드 아키텍처 상세 설계

> **범위 변경 (2026-09-21)**: Gmail 단독 지원으로 한정됨에 따라 네이버 폴링 워커/큐 관련 구성을 모두 제거했다. 또한 MVP는 LLM을 사용하지 않기로 결정해 `llm-classifier.service.ts`를 규칙 기반 추출기 모듈로 대체했다 (`00-개요.md`, `02-쿠폰판별로직.md` 참고).

원본 설계의 기술 스택 표와 모듈 목록을 실제 폴더 구조/큐 설계 수준까지 구체화한다.

## 모듈/폴더 구조 (NestJS 기준 제안)

```
src/
  auth/                 # AuthService: OAuth 플로우, 세션 JWT 발급
    gmail.provider.ts
    mail-provider.interface.ts
  mail-ingest/           # MailIngestService: webhook 수신, 보정 폴링, 중복 제거
    gmail-webhook.controller.ts
    gmail-safety-poll.processor.ts
    mail-ingest.processor.ts   # BullMQ 워커
  coupon-classifier/     # CouponClassifierService: 규칙 필터 + 정규식 추출/판정
    rule-filter.service.ts
    extractors/
      coupon-extractor.interface.ts
      generic-regex.extractor.ts
      coupang.extractor.ts       # 발신자 전용 파서 (베타 기간 계속 추가)
      baemin.extractor.ts
    validity-checker.service.ts   # 만료일 기반 usable_now 판정
  notification/          # NotificationService: FCM 발송, 재시도
    push-dispatch.processor.ts
    fcm.client.ts
  user/                  # UserService: 계정/설정 관리
  coupons/               # Coupon CRUD 컨트롤러
  devices/               # Device 등록 컨트롤러
  common/
    encryption/          # AES-256-GCM 유틸 (07번 문서 참고)
    queue/                # BullMQ 큐 정의 공통 모듈
```

## 큐(Queue) 설계 상세

| 큐 이름 | 목적 | Producer | Consumer | 동시성(concurrency) |
| --- | --- | --- | --- | --- |
| `mail-ingest` | 신규 메일 감지 → 파싱 트리거 | Gmail webhook, 보정 폴링 잡 | `MailIngestProcessor` | 계정당 1 (동일 계정 순서 보장), 전체 워커 20 |
| `coupon-classify` | 규칙 필터 + 정규식 추출/판정 (MVP: LLM 미사용) | `MailIngestProcessor` | `CouponClassifierProcessor` | 외부 API 호출이 없어 CPU 코어 수에 맞춰 조절 (초기 10) |
| `push-dispatch` | FCM/APNs 발송 | `CouponClassifierProcessor` | `PushDispatchProcessor` | 50 (외부 호출 병목 적음) |
| `gmail-watch-renewal` | Pub/Sub watch 갱신 (반복 잡) | 크론 | `WatchRenewalProcessor` | 5 |
| `gmail-safety-poll` | webhook 유실 대비 보정 폴링 (반복 잡, 매 6시간) | 크론 | `SafetyPollProcessor` | 5 |
| `coupon-expiry-reminder` | 만료 임박 리마인더 (반복 잡, 매일 09:00 KST) | 크론 | `ExpiryReminderProcessor` | 1 |

각 큐는 실패 시 별도의 Dead Letter Queue(DLQ) 성격의 `*-failed` 큐로 이동시켜, 자동 재시도 소진 후에도 실패한 작업을 운영자가 수동 확인할 수 있게 한다.

## 인프라 구성 (초기 규모 기준)

- API 서버: ECS Fargate 또는 K8s Deployment, 오토스케일링 (CPU 60% 기준)
- 워커: API 서버와 별도 서비스로 분리 배포 (트래픽 폭주 시 API 응답성에 영향 없도록)
- Redis: ElastiCache 또는 관리형 Redis (BullMQ 큐 + 세션 캐시 겸용, 초기엔 단일 인스턴스로 충분)
- PostgreSQL: RDS/Cloud SQL, 초기 단일 인스턴스 + 자동 백업, 사용자 증가 시 읽기 복제본 추가 검토
- 비밀 관리: Secrets Manager에 OAuth 클라이언트 시크릿, AES 암호화 키(KMS 키로 감싸는 envelope encryption) 저장

## 환경 분리

- `dev` (로컬 개발, 테스트 계정만), `staging` (내부 베타), `production` 3단계 환경을 초기부터 분리
- Gmail OAuth는 환경별로 별도 GCP 프로젝트/클라이언트 ID 사용 (심사 전 unverified 테스트가 production에 영향 없도록)

## 로깅/모니터링 최소 셋업 (MVP 단계)

- Sentry: API 서버 + 워커 프로세스 모두 연동, 릴리즈 태깅으로 배포 버전 추적
- 구조화 로그(JSON): `userId`(또는 해시), `mailAccountId`, `jobId`를 항상 포함해 특정 사용자의 처리 흐름을 추적 가능하게 함 — 단, 메일 제목/본문 등 콘텐츠는 로그에 남기지 않음 (07번 문서 원칙과 연결)
- 핵심 대시보드 패널: 큐별 대기 길이, 처리 지연시간(p50/p95), `extraction_failed` 비율(발신자별), 푸시 발송 성공률
