# 02. 쿠폰 판별 로직 상세 설계 ★ 심화

> **MVP 범위 변경 (2026-09-21)**: MVP는 **LLM(AI 모델)을 사용하지 않는다.** 전량 규칙/정규식 기반으로 판별하며, LLM 도입은 MVP 출시 이후 정확도 개선이 필요할 때 검토하는 별도 과제로 미룬다 (`00-개요.md` 참고). 이 문서는 원래 "규칙 필터 → LLM 판별" 2단계였던 파이프라인을 "규칙 필터 → 규칙 기반 추출/판정" 구조로 다시 설계한 버전이다.

## 파이프라인 개요 (재정리)

```
신규 메일
  → [1단계] 규칙 필터 (도메인/키워드 매칭)
      → 불일치: 폐기 (DB 기록 없음)
      → 일치: 2단계로
  → [2단계] 구조화 추출 (발신자 전용 파서 → 없으면 범용 정규식 파서)
      → 만료일 파싱 실패: 보류(미발송, 로그만 남김 — 파서 보강 대상)
      → 스팸성 문구 매칭: 폐기
      → 만료일 파싱 성공 & 만료 전: 3단계로
  → [3단계] 유효성 판정 (규칙 기반, 100% 결정론적)
      → 만료됨: 폐기
      → 유효함: 푸시 발송 큐로 전달
```

LLM을 쓰던 구조와 비교하면, "애매한 경우를 사람처럼 판단"하는 능력은 포기하는 대신 **비용이 0원이고, 판정 근거가 100% 설명 가능(regex 매칭 결과 그대로)**하다는 장점이 있다. 정밀도가 LLM 대비 낮을 수 있다는 점은 감수하고, 베타 단계에서 발신자별 파서를 계속 보강하는 방식으로 커버리지를 넓혀간다.

## 1단계: 규칙 필터 (기존과 동일)

도메인 화이트리스트 + 키워드 매칭 구조는 이전 설계와 동일하게 유지한다.

```sql
CREATE TABLE filter_domains (
  id SERIAL PRIMARY KEY,
  domain VARCHAR(255) NOT NULL,
  is_global BOOLEAN DEFAULT true,
  user_id UUID REFERENCES users(id),
  created_at TIMESTAMPTZ DEFAULT now()
);

CREATE TABLE filter_keywords (
  id SERIAL PRIMARY KEY,
  keyword VARCHAR(100) NOT NULL,
  lang VARCHAR(10) DEFAULT 'ko',
  weight SMALLINT DEFAULT 1,
  created_at TIMESTAMPTZ DEFAULT now()
);
```

초기 키워드 시드: `쿠폰`, `할인코드`, `프로모션`, `적립금`, `%할인`, `%OFF`, `무료배송`, `이벤트`, `coupon`, `promo code`, `discount code`, `% off`, `special offer`

## 2단계: 구조화 추출 (CouponExtractor)

### 인터페이스 설계

발신자마다 메일 포맷이 다르므로, 발신자별 전용 파서를 우선 적용하고 없으면 범용 정규식 파서로 폴백하는 구조로 설계한다. 이렇게 하면 향후 LLM을 다시 도입할 때도 `CouponExtractor` 구현체 하나만 추가하면 되므로 구조를 재사용할 수 있다.

```ts
interface CouponExtractor {
  readonly extractorType: 'sender_specific' | 'generic_regex' | 'llm'; // 향후 'llm' 확장 대비
  canHandle(senderDomain: string): boolean;
  extract(subject: string, bodyText: string): ExtractedCoupon | null;
}

interface ExtractedCoupon {
  discount: string | null;
  expiryDate: string | null;   // ISO 8601 (YYYY-MM-DD), 파싱 실패 시 null
  conditions: string | null;
  isSpammy: boolean;           // 스팸성 문구 매칭 여부
  extractorId: string;         // 어떤 파서가 처리했는지 (디버깅/개선용)
}
```

### 발신자 전용 파서 (Sender-specific Extractor)

원본 설계의 도메인 화이트리스트에 등록된 주요 발신자(쿠팡, 배달의민족, 항공사 등)는 메일 포맷이 대체로 고정되어 있으므로, 발신자 도메인별로 전용 정규식 파서를 하나씩 작성한다.

```ts
// 예시: 쿠팡 전용 파서
class CoupangExtractor implements CouponExtractor {
  extractorType = 'sender_specific' as const;
  canHandle(domain: string) { return domain === 'coupang.com'; }
  extract(subject: string, body: string): ExtractedCoupon | null {
    const discountMatch = body.match(/(\d{1,2})%\s*할인/);
    const dateMatch = body.match(/(\d{1,2})\/(\d{1,2})까지/) ?? body.match(/(\d{4})-(\d{2})-(\d{2})까지/);
    const conditionMatch = body.match(/([\d,]+원)\s*이상\s*구매\s*시/);
    // ... 쿠팡 메일 포맷에 맞춘 세부 파싱 로직
    return {
      discount: discountMatch ? `${discountMatch[1]}%` : null,
      expiryDate: parseKoreanDate(dateMatch),
      conditions: conditionMatch ? `${conditionMatch[1]} 이상 구매 시` : null,
      isSpammy: false,
      extractorId: 'coupang_v1',
    };
  }
}
```

베타 초기에는 사용자 트래픽이 몰리는 상위 5~10개 발신자(쇼핑몰, 배달앱, 항공사 등)를 우선 지원 대상으로 삼고, 실제 메일 샘플을 수집해 파서를 하나씩 작성한다.

### 초기 지원 발신자 선정 절차 (2026-09-21 확정)

전용 파서를 만들 초기 발신자 목록을 지금 추측으로 정하지 않는다. 파서는 실제 메일 샘플이 있어야 정규식을 작성할 수 있고, 근거 없이 고른 발신자는 사용자 메일함에 실제로 오지 않을 수 있기 때문이다. 대신 아래 **절차**를 확정하고, 목록은 1단계 착수와 동시에 데이터로 채운다.

1. **집계** — 본인과 지인의 Gmail 계정 3~5개에서 최근 90일 프로모션 메일을 발신자 도메인별로 집계한다 (일회성 스크립트, 반나절 규모). 이 단계에서 수집한 실제 메일 본문이 곧 파서 작성용 샘플이 된다.
2. **선정** — 빈도 상위 순으로 뽑되, 특정 카테고리에 쏠리지 않도록 아래 슬롯을 채우는 방식으로 8곳을 고정한다.

   | 카테고리 | 슬롯 |
   | --- | --- |
   | 이커머스 | 3 |
   | 배달·외식 | 2 |
   | 뷰티·리테일 | 1 |
   | 항공·여행 | 1 |
   | 카페·편의점 | 1 |

3. **활용** — 확정된 목록은 `filter_domains` 초기 시드 데이터와 발신자 전용 파서 작업 목록으로 동시에 사용한다.

1단계(MVP 백엔드)와 병행 가능한 작업이므로 착수 블로커로 두지 않는다 (`09-배포및로드맵.md` 참고).

### 범용 정규식 파서 (Generic Fallback Extractor)

전용 파서가 없는 발신자는 아래와 같은 범용 패턴으로 최대한 추출을 시도한다.

| 항목 | 패턴 예시 |
| --- | --- |
| 할인율/금액 | `(\d{1,2})%\s*(할인\|OFF\|off)`, `([\d,]+)\s*원\s*할인` |
| 만료일 (상대) | `(\d{1,2})/(\d{1,2})\s*까지`, `~\s*(\d{1,2})/(\d{1,2})` |
| 만료일 (절대) | `(\d{4})[-.](\d{1,2})[-.](\d{1,2})` |
| 조건 | `([\d,]+원)\s*이상\s*(구매\|결제)\s*시`, `([\w가-힣]+)\s*한정` |
| 스팸성 문구 (블랙리스트) | `설문조사`, `무료체험\s*신청`, `회원가입만\s*해도`, `지금\s*안\s*사면`, `마지막\s*기회`(할인 정보 없이 단독 등장 시) |

범용 파서는 발신자 전용 파서보다 정확도가 떨어질 수 있음을 인지하고, `extractorId: 'generic_v1'`로 태깅해 베타 단계에서 어떤 발신자들이 범용 파서로만 처리되고 있는지(= 전용 파서 작성이 필요한 후보) 추적한다.

## 3단계: 유효성 판정 (100% 규칙 기반)

```
usable_now 판정 로직:
1. isSpammy === true            → false (폐기)
2. expiryDate === null          → false (보류 — 파싱 실패, 발송하지 않음)
3. expiryDate < 오늘            → false (만료됨)
4. expiryDate >= 오늘           → true  (발송 대상)
```

LLM 버전에 있던 `confidence`(0.0~1.0 신뢰도)는 없앤다. 대신 `extractorId`로 "발신자 전용 파서가 처리했는지, 범용 파서가 처리했는지"를 구분해 기록하고, 이 값 자체가 신뢰도의 대리 지표 역할을 한다 (전용 파서 결과가 범용 파서보다 신뢰도가 높다고 간주).

### 만료일 파싱 실패 시 처리 (원본에 없던 MVP 전용 정책)

LLM 버전과 달리 규칙 기반은 "이 문장이 애매하니 confidence를 낮춰서 처리"하는 유연함이 없다. 따라서 만료일을 못 찾으면 **무조건 보류**하는 보수적인 정책을 취한다. 이렇게 놓친 메일은:

- `processed_mails.filter_result = 'extraction_failed'`로 기록
- 주 1회 운영자가 `extraction_failed` 목록을 샘플링 검토해, 자주 등장하는 발신자가 있으면 해당 발신자의 전용 파서를 작성해 커버리지를 넓힌다
- 이 반복이 곧 "베타 단계에서 파서를 계속 보강한다"는 운영 루틴이다 (아래 "운영 중 정확도 측정 방법" 참고)

## 만료 임박 리마인더

기존 설계와 동일하게 유지한다. `coupons` 테이블에서 `expiry_date`가 1일 이내로 남았고 아직 리마인더를 보내지 않은 유효 쿠폰을 매일 09:00 KST에 스캔하는 배치 잡(`coupon-expiry-reminder`)을 둔다.

## 운영 중 정확도 측정 방법 (규칙 기반 버전)

1. **오탐지(false positive) 측정**: 발송된 알림에 "이 쿠폰 정확했나요? 👍👎" 피드백 버튼을 붙여 실측
2. **미탐지(false negative) 프록시**: 규칙 필터에서 통과했지만 `extraction_failed`로 보류된 메일을 주간 리포트로 뽑아, 사람이 직접 열어보고 실제 쿠폰이었는지 확인 → 실제 쿠폰이었다면 해당 발신자용 전용 파서를 다음 스프린트에 추가
3. 발신자별 "전용 파서 적용 여부", "extraction_failed 비율"을 대시보드에 노출해 파서 보강 우선순위를 정한다

## 향후 LLM 도입 시 확장 경로 (참고용, MVP 범위 아님)

MVP 운영 후 오탐지/미탐지 비율이 목표치를 넘거나, 파서 유지보수 비용이 감당하기 어려워지면 LLM 판별을 다시 검토할 수 있다. 그때는:

- `CouponExtractor` 인터페이스를 구현하는 `LlmExtractor`를 추가하기만 하면 되므로, 지금 구조를 갈아엎을 필요가 없다
- `extraction_failed`로 쌓인 메일들이 이미 "규칙으로는 못 푸는 어려운 케이스" 샘플 데이터가 되어, LLM 프롬프트 설계나 비용 추정에 바로 활용 가능하다
- 이전 설계 초안(LLM 프롬프트, confidence 정책, 캐싱 전략)은 git 히스토리에 남아있으니 그대로 참고 가능하다
