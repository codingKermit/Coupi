# 02. 쿠폰 판별 로직 상세 설계 ★ 심화

원본 설계의 "쿠폰 판별 로직 설계" 섹션을 구현 가능한 수준까지 구체화한다. 이 문서는 이번 라운드에서 가장 우선적으로 다듬은 영역이다.

## 파이프라인 개요 (재정리)

```
신규 메일
  → [1단계] 규칙 필터 (도메인/키워드 매칭)
      → 불일치: 폐기 (DB 기록 없음)
      → 일치: 2단계로
  → [2단계] LLM 판별 (구조화 출력)
      → confidence < 0.7: 폐기 (보수적 처리)
      → usable_now = false: 폐기
      → usable_now = true & confidence >= 0.7: 3단계로
  → [3단계] 중복/캐시 체크
      → 캐시 히트 (동일 패턴 처리 이력 있음): LLM 결과 재사용, 호출 생략
      → 캐시 미스: 위 LLM 결과를 캐시에 적재
  → 푸시 발송 큐로 전달
```

## 1단계: 규칙 필터 상세

### 데이터 모델
규칙을 코드에 하드코딩하지 않고 DB 테이블로 관리해, 운영 중 튜닝이 가능하도록 한다.

```sql
CREATE TABLE filter_domains (
  id SERIAL PRIMARY KEY,
  domain VARCHAR(255) NOT NULL,      -- 예: 'coupang.com', 'baemin.com'
  is_global BOOLEAN DEFAULT true,    -- true: 전체 사용자 공통, false: 사용자 개별 등록
  user_id UUID REFERENCES users(id), -- is_global=false일 때만 사용
  created_at TIMESTAMPTZ DEFAULT now()
);

CREATE TABLE filter_keywords (
  id SERIAL PRIMARY KEY,
  keyword VARCHAR(100) NOT NULL,     -- 예: '쿠폰', '%할인', 'coupon'
  lang VARCHAR(10) DEFAULT 'ko',
  weight SMALLINT DEFAULT 1,         -- 향후 스코어링 필터로 확장 대비
  created_at TIMESTAMPTZ DEFAULT now()
);
```

### 매칭 로직
1. 발신자 이메일의 도메인이 `filter_domains`(전역 또는 해당 사용자 개별 등록)에 있으면 즉시 통과 (키워드 검사 생략 — 신뢰 발신자이므로)
2. 도메인이 화이트리스트에 없으면 제목에서 `filter_keywords`와 대소문자 무관 부분 문자열 매칭. 하나라도 매칭되면 통과
3. 두 조건 모두 불일치 → 폐기. 폐기된 메일은 로그에만 남기고 (`filtered_out_count` 메트릭 증가) 저장하지 않음 (개인정보 최소화 원칙)

### 초기 키워드 시드 목록 (한국어 + 영어)
`쿠폰`, `할인코드`, `프로모션`, `적립금`, `%할인`, `%OFF`, `무료배송`, `이벤트`, `coupon`, `promo code`, `discount code`, `% off`, `special offer`

운영 중 발신자 도메인별 정탐/오탐 비율을 대시보드로 확인하며 키워드를 보강한다.

### 목표 통과율
- 원본 설계의 "90% 이상 필터링" 목표를 측정 가능하게 만들기 위해, `filter_pass_rate` 메트릭을 일 단위로 집계하고 90%를 초과(즉 필터를 너무 많이 통과시킴)하면 알림을 발생시킨다.

## 2단계: LLM 판별 상세

### 프롬프트 설계

시스템 프롬프트(고정):

```
당신은 이메일 본문을 분석해 실제로 사용 가능한 할인 쿠폰인지 판별하는 어시스턴트입니다.
반드시 아래 JSON 스키마로만 응답하세요. 스키마 외 텍스트를 출력하지 마세요.

판단 기준:
1. 만료일이 오늘(기준일: {{today}}) 이후인가?
2. 사용 조건(최소 구매금액, 특정 카테고리 한정 등)이 명시되어 있고 합리적으로 충족 가능한가?
3. 스팸성 과장 문구("지금 안 사면 후회", 무기한 "선착순" 등 구체적 근거 없는 긴급성 조장)만 있고 실질적 할인 정보가 없는 경우 쿠폰이 아닌 것으로 간주한다.
4. 이미 종료된 이벤트를 회고하는 뉴스레터(예: "지난 세일 감사합니다")는 쿠폰이 아니다.

불확실하면 confidence를 낮게 설정하세요. 절대 추측으로 만료일을 지어내지 마세요 — 본문에 명시되지 않았다면 expiry_date를 null로 두세요.
```

사용자 메시지: 메일 제목 + 발신자 + 본문(텍스트 변환, HTML 태그 제거, 최대 4000자로 truncate)

### 출력 스키마 (구조화 출력 강제)
```json
{
  "is_coupon": "boolean",
  "discount": "string | null",
  "expiry_date": "string (YYYY-MM-DD) | null",
  "conditions": "string | null",
  "usable_now": "boolean",
  "confidence": "number (0.0~1.0)",
  "reason": "string — 판정 근거 한 줄 요약 (디버깅/운영자 검토용, 사용자에게는 노출 안 함)"
}
```
`reason` 필드를 원본 설계에 추가했다: confidence가 낮거나 오탐지 신고가 들어왔을 때 운영자가 원인을 빠르게 파악하기 위함이다.

### expiry_date가 없는 경우 처리
- `expiry_date: null`이면서 `usable_now: true`인 경우, 만료일 미표시 쿠폰으로 간주해 알림 문구를 "만료일 확인 필요"로 표시하고, 발송 7일 후 자동 만료 처리(재검토 큐에 재투입)하는 기본 정책을 둔다.

### confidence 임계값 정책
- `< 0.7`: 폐기 (원본 설계와 동일)
- `0.7 ~ 0.85`: 발송하되, 알림 본문에 "(확인 필요)" 같은 부가 표시 없이 정상 발송 — 단, 이 구간은 별도로 로그를 남겨 주 1회 사람이 샘플링 검토
- `> 0.85`: 정상 발송

### LLM 실패/타임아웃 처리
- LLM 호출이 타임아웃(예: 10초) 또는 API 오류를 반환하면 최대 2회 재시도(지수 백오프), 그래도 실패하면 해당 메일은 "판별 보류" 상태로 `pending_review` 큐에 남기고 폐기하지 않는다. 5분 후 재시도 잡이 자동 재처리한다. (자세한 내용은 08-에러처리및엣지케이스.md)

## 3단계: 캐싱 및 중복 호출 방지

### 캐시 키 설계
동일 발신자가 매주 같은 형식의 프로모션 메일을 보내는 경우를 잡아내기 위한 캐시.

```sql
CREATE TABLE coupon_pattern_cache (
  id SERIAL PRIMARY KEY,
  sender_domain VARCHAR(255) NOT NULL,
  subject_pattern VARCHAR(500) NOT NULL, -- 제목에서 날짜/숫자를 정규화한 템플릿, 예: "쿠팡 {N}% 할인 쿠폰 도착"
  last_llm_result JSONB NOT NULL,
  hit_count INT DEFAULT 1,
  updated_at TIMESTAMPTZ DEFAULT now(),
  UNIQUE(sender_domain, subject_pattern)
);
```

### 정규화 규칙
제목에서 다음을 플레이스홀더로 치환 후 패턴 매칭:
- 숫자(할인율, 금액) → `{N}`
- 날짜 형식(9/30, 2026-09-30 등) → `{DATE}`
- 쿠폰 코드로 추정되는 8자 이상 영숫자 조합 → `{CODE}`

### 캐시 사용 정책
- 패턴이 일치해도 **만료일(expiry_date)만은 매번 본문에서 재파싱**한다 (LLM 재호출 없이 정규식으로 날짜만 추출) — 캐시된 결과의 discount/conditions는 재사용하되 expiry_date는 항상 최신 메일 기준으로 갱신
- 캐시 적중률이 낮은(hit_count가 3 미만인) 패턴은 30일 후 자동 삭제해 캐시 테이블 비대화 방지

## 만료 임박 리마인더

- `coupons` 테이블에서 `expiry_date`가 1일 이내로 남았고 아직 리마인더를 보내지 않은 유효 쿠폰을 매일 09:00 KST에 스캔하는 배치 잡(`coupon-expiry-reminder`)을 둔다.
- 리마인더는 원본 쿠폰 알림과 구분되는 별도 알림 타입(`notification_type = 'expiry_reminder'`)으로 발송해, 사용자가 알림 설정에서 두 종류를 개별 on/off할 수 있게 한다.

## 운영 중 정확도 측정 방법

1. **정밀도(Precision) 측정**: 베타 단계에서 발송된 알림에 "이 쿠폰 정확했나요? 👍👎" 피드백 버튼을 붙여 실측 (06번 문서, Open Question #5와 연결)
2. **재현율(Recall) 프록시**: 규칙 필터에서 폐기된 메일 중 일부(예: 1%)를 샘플링해 LLM으로 재검사, 실제 쿠폰이 필터 단계에서 누락되고 있는지 주기적으로 확인
3. 두 지표를 주간 리포트로 Datadog/Grafana 대시보드에 노출
